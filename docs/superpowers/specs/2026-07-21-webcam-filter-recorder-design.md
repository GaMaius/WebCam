# 실시간 웹캠 필터 + 녹화 수집 웹사이트 설계

## 목적

웹캠 영상을 실시간으로 재미있는 시각 필터(하프톤 도트 / ASCII 아트 / 엣지 스케치)로 변환해 보여주는 가벼운 웹사이트를 만든다. 얼굴 특징이 알아볼 수 있게 유지되는 것이 핵심이며, 익명화는 목적이 아니다. 동시에 원본 웹캠 영상을 사용자 소유 서버에 녹화·저장해 데이터를 수집한다. 친구/지인 여러 명이 데스크톱과 모바일을 가리지 않고 동시에 접속해 사용한다.

## 아키텍처 개요

```
[브라우저 (사용자/친구들)]
   ├─ getUserMedia로 웹캠 스트림 획득
   ├─ <video> (숨김, 원본 소스) → <canvas>에 필터 렌더링 (화면 표시용)
   ├─ MediaRecorder로 "원본" 스트림 녹화 → webm 청크 생성
   └─ fetch POST로 청크를 서버에 스트리밍 업로드
        │
        ▼
[Node.js 서버 (Express, 사용자 PC에서 실행)]
   ├─ 정적 파일 서빙 (프론트엔드 HTML/JS)
   ├─ /session/start, /upload, /session/end 엔드포인트
   └─ 세션별 파일로 청크를 디스크에 순서대로 append 저장
        │
        ▼
[localtunnel으로 외부 노출] → 친구들이 URL로 접속
```

화면에 보이는 필터 캔버스와 서버로 전송되는 녹화 스트림은 서로 다른 소스다. 필터는 순수 화면 연출이고, 녹화는 `<video>` 엘리먼트의 원본 스트림을 그대로 `MediaRecorder`에 연결한다.

## 프론트엔드 필터 엔진

- 렌더링 방식: **Canvas2D 픽셀 연산** (WebGL 셰이더 아님). GPU 의존성이 없고, 구현/유지보수가 단순하며, 사용자의 iGPU(Radeon 740M) 사양에도 무리 없이 동작한다.
- 공통 유틸: 비디오 프레임을 `N×N` 블록으로 순회하며 블록별 평균 밝기/색상을 계산 (CNN pooling과 동일한 구조).
- **하프톤/도트** (기본값): 블록 평균 밝기 → 밝기에 비례한 반지름의 원(dot)을 블록 중심에 그림.
- **ASCII 아트**: 블록 평균 밝기 → 문자셋(` .:-=+*#%@` 등)에 매핑해 해당 위치에 문자 렌더링.
- **엣지 스케치**: Sobel 커널로 그레이스케일 엣지 강도 계산 → 임계값 이상인 픽셀만 검게, 나머지는 흰 배경.
- UI: 상단에 필터 선택 토글 버튼 3개 + 블록/도트 크기 슬라이더(2px~40px).
- `requestAnimationFrame` 루프로 매 프레임 처리. 블록 크기가 클수록 연산량이 줄어드는 구조라 슬라이더가 성능 조절 역할도 겸한다.

## 모바일 대응

- **카메라**: 기본은 전면 카메라(`facingMode: 'user'`)로 시작하고, 전/후면 전환 버튼을 둔다(`navigator.mediaDevices.enumerateDevices()`로 카메라가 2개 이상이면 버튼 노출).
- **레이아웃**: 고정 픽셀 기반 데스크톱 레이아웃 대신 반응형 CSS(flexbox + `max-width: 100%`, `viewport` meta 태그)로 구성. 좁은 화면(모바일 세로모드)에서는 캔버스가 화면 폭에 맞춰 축소되고, 필터 토글/슬라이더는 캔버스 아래로 세로 스택.
- **터치 컨트롤**: 필터 토글 버튼과 슬라이더는 터치 타깃 크기를 44px 이상으로 확보(iOS HIG 권장 기준). `<input type="range">`는 네이티브로 터치 지원되므로 그대로 사용.
- **캔버스 해상도**: 모바일에서는 기기 성능 편차가 크므로 `getUserMedia`의 `width`/`height` 제약을 기기 화면 폭 기준으로 낮춰 요청(예: 최대 640px 폭)하여 필터 연산량과 발열을 줄인다.
- **화면 꺼짐 방지**: 웹캠 사용 중 화면이 꺼지면 스트림이 끊길 수 있으므로 `Screen Wake Lock API`(지원 브라우저 한정)로 화면 꺼짐을 방지, 미지원 브라우저에서는 무시(폴백 없음, 필수 기능 아님).

## 녹화 & 업로드 파이프라인

- 저장 대상은 **필터가 적용되지 않은 원본 웹캠 화면**이다.
- "웹캠 시작" 클릭 → `getUserMedia` 권한 요청 → 성공 시 서버에 `POST /session/start` 호출해 세션 ID(uuid) 발급받음.
- **브라우저별 코덱 호환성**: iOS Safari의 `MediaRecorder`는 `video/webm`을 지원하지 않고 `video/mp4`(H.264)만 지원한다. Android Chrome/데스크톱 브라우저는 반대로 webm이 기본이다. 따라서 고정 mimeType 대신 `MediaRecorder.isTypeSupported()`로 `video/webm;codecs=vp8,opus` → `video/mp4` 순으로 확인해 사용 가능한 쪽을 선택하고, `/session/start` 호출 시 선택된 포맷(확장자)을 서버에 함께 전달해 세션 메타데이터에 기록한다.
- `MediaRecorder(stream, { mimeType: <감지된 값> })`를 `timeslice`(예: 3초)로 시작 → `ondataavailable`마다 해당 청크를 `POST /upload/:sessionId`로 순서대로 전송.
- 탭 종료/웹캠 끄기 시 `mediaRecorder.stop()` → 마지막 청크 전송 후 `POST /session/end` 호출로 파일 마무리.
- 청크 전송 실패 시 1회 재시도. 실패해도 로컬 녹화 자체는 계속 진행하여 끊긴 구간만 유실되고 전체 세션은 끊기지 않게 한다.
- 인코딩은 각 클라이언트(친구들 포함)의 브라우저에서 자체적으로 수행되므로, 서버를 구동하는 컴퓨터의 사양과 무관하다.

## 서버 (Node.js + Express)

- `POST /session/start` → 세션 ID 발급, 클라이언트가 알려준 포맷에 맞춰 `recordings/{sessionId}.webm` 또는 `recordings/{sessionId}.mp4` 파일 스트림 오픈.
- `POST /upload/:sessionId` → 받은 청크(raw body)를 해당 파일에 순서대로 append.
- `POST /session/end` → 파일 스트림 close.
- 세션 ID로 완전히 분리되므로 여러 명이 동시 접속해도 파일 핸들 충돌이 없다.
- 서버는 트랜스코딩/재인코딩을 하지 않고 청크를 그대로 디스크에 쓰기만 하므로 연산 부하가 거의 없다.

## 외부 노출 & 최소 보안

- 로컬에서 `node server.js` 실행 후 `localtunnel`로 외부 공개 (기존에 사용해본 방식 재사용).
- URL 노출 시 낯선 사람이 업로드 엔드포인트를 두드릴 수 있으므로, 프론트가 서버에 요청할 때 실어 보내는 간단한 접근 코드(shared token)를 둔다. `.env`에 토큰을 저장하고, 프론트 접속 시 코드를 입력받아 요청 헤더에 실어 보낸다. 이는 인증 시스템이 아니라 낯선 사용자의 스팸 업로드를 막는 최소한의 문지방이다.
- 친구들이 접속했을 때 "이 화면은 촬영되어 저장됩니다" 안내 문구를 페이지에 표시할 것을 권장한다(필수는 아님, 제안).

## 하드웨어 적합성 (AMD Ryzen 5 8500G / Radeon 740M)

- 필터 처리는 GPU 비의존 Canvas2D 방식이라 iGPU 성능과 무관하게 동작한다. 640×480 해상도의 블록 연산은 Zen4 6코어 CPU에 매우 가벼운 부하다.
- 녹화 인코딩은 각 사용자의 브라우저가 자신의 기기에서 수행하므로, 서버를 구동하는 호스트 컴퓨터에는 친구들 영상의 인코딩 부하가 걸리지 않는다.
- Radeon 740M은 VCN 하드웨어 인코더(H.264/H.265/AV1)를 내장하고 있어, 호스트 자신이 접속해 녹화할 때도 브라우저가 하드웨어 인코딩을 활용할 수 있다.
- 서버는 청크를 그대로 append만 하는 구조라 트랜스코딩 부하가 없다.
- 결론: 별도 스펙 변경 없이 현재 설계 그대로 진행 가능.

## 테스트 방향

- 필터 3종 각각 브라우저에서 실시간으로 눌러보며 프레임 드랍/버벅임 여부 육안 확인.
- 도트/블록 크기 슬라이더를 최소~최대로 움직여 성능 변화 확인.
- 웹캠 시작 → 일정 시간 진행 → 종료 후 `recordings/` 폴더에 정상적인 webm 파일이 생성되고 재생 가능한지 확인.
- 브라우저 탭 2개(또는 기기 2대)로 동시 접속해 세션이 서로 다른 파일로 분리 저장되는지 확인.
- localtunnel URL로 외부 기기에서 접속 테스트.
- 모바일 브라우저(iOS Safari, Android Chrome)에서 실제 접속해: 레이아웃이 화면 폭에 맞게 반응형으로 보이는지, 전/후면 카메라 전환이 되는지, 녹화 후 서버에 mp4/webm 파일이 정상 생성·재생되는지 확인.
